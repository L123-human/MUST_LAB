## 代码和数据设计

`personal.js` 是独立规则层，提供 `empty`、`valid`、`change`、`tier` 和字符计数；它不负责身份验证。`main.js` 负责页面、操作消息、读写存储及排序整合。`index.html` 新增收藏导航，并先载入规则层；CSS 复用原有暖色和健康主题。

- 演示数据：`localStorage.canteen_personal_demo_v1 = { favorites: [dishId], feedback: { [dishId]: { mark, text } } }`。
- 演示开关：当前标签页的 `sessionStorage.canteen_personal_demo_active`。默认关闭；主动开启。退出隐藏数据但保留本地记录，重新开启可恢复。
- 这是此浏览器共享的演示数据，任何共用该浏览器的人都可能查看；界面明确提示。没有模拟密码、伪造登录或宣称安全隔离。不要保存敏感信息。
- 原有 `canteen_logs`、`canteen_prefs`、`canteen_goal` 与主题存储键不变；不迁移或删除旧饮食记录。
- 每次写前重读记录，接收 `storage` 事件更新其他标签页。仍没有跨窗口同时写入的事务保障；正式版本应由服务端事务处理。
- 当前原型无 `availability` / `verification` 数据；不能宣称完整实现 §6.4 对可用性和食材核验的过滤。此项等待 B 的菜单数据接口。

## A / B / C 联调接口

A：用真实会话替代 `demoActive`；用基于会话的服务端读写替换 `readPersonal` / `changePersonal` 中的存储步骤。服务端从会话识别用户，不信任客户端传入账号 ID。服务端重复验证 20 项上限、重复收藏、菜品存在、标记枚举和文字长度；并发收藏用事务约束。登录/退出时清除内存和草稿、重取当前账号数据。不要自动把共享演示记录归入某个账户。

B：继续提供稳定唯一的菜品 ID 与摊位信息；新增菜单状态后处理下架/删除菜品的展示和清理策略。当前对不存在的菜品拒绝写操作；已有但缺失的收藏保留并提示，避免静默丢失记录。

C：已在 `visibleDishes` 接入反馈同分层和 5 项上限；排序仍以口味匹配数为第一排序项。正式账户接入后只使用当前账号的反馈。`logs`、收藏、文字内容均不作推荐权重。

正式联调必须补：游客与过期会话拒绝、A/B 两账号读写隔离、伪造账号/直接请求、刷新和退出后的隔离、并发容量、服务端失败回滚。仅在这些通过后才能报告 SEC-1.2 完成。
